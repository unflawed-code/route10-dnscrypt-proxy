# Supply Chain Verification

This repo uses the official SLSA GitHub Generator for release artifacts produced by the `SLSA Provenance` workflow:

- CI runs shell syntax checks and hermetic tests.
- Tags matching `v*` build a release tarball from the exact Git commit.
- Release artifacts include `SHA256SUMS`.
- `slsa-framework/slsa-github-generator` generates signed SLSA Build L3 provenance for the release tarball.

The badge means release artifacts have SLSA Build L3 provenance generated by the official reusable workflow. It is not a dynamic certification badge or repo-wide conformance claim; the proof is the generated `.intoto.jsonl` provenance that users verify.

For the SLSA model and levels, see [slsa.dev](https://slsa.dev/).

## Release Artifacts

For tag `vX.Y.Z`, the release workflow publishes:

```text
route10-dnscrypt-proxy-vX.Y.Z.tar.gz
route10-dnscrypt-proxy-vX.Y.Z.tar.gz.sig   (added by hand, see below)
SHA256SUMS
*.intoto.jsonl
```

## Update-Boundary Trust: Release Signatures

Checksums and provenance both come from the same place as the artifact, so a
compromised repository can publish all three consistently. The device updater
(`scripts/updater.sh`) therefore requires a **detached signature** over the
release archive, verified against a public key it already holds.

- `lib/vendor/route10-signature.sh` - vendored copy of
  `route10-update-verifier` 1.0.0, pinned by
  `lib/vendor/route10-signature.sh.sha256`. CI runs `sha256sum -c` on it, so a
  hand-edited verifier cannot ship. Never edit these two files by hand; re-run
  `sync-verifier.sh` from the upstream project instead.
- `conf/release-pub.pem` - the trust anchor. The updater restores this file
  after applying a release and refuses to update when the signature, the
  `.sig` asset, or this key is missing.

Current trust anchor: SHA-256 over the DER-encoded public key.

```text
367ebdcc2b6a99048415df3ee68a017b0579db421c9750c5d37edd4cf7783a1d
```

Print it on a checkout or on a device before trusting an update:

```bash
openssl pkey -pubin -in conf/release-pub.pem -outform DER | sha256sum
```

A copy of this fingerprint, signed with the release key, is mirrored outside the
repository at
[gist.github.com/unflawed-code/54722b59bf2408d54356ec6495a89098](https://gist.github.com/unflawed-code/54722b59bf2408d54356ec6495a89098).
The gist is hosted under the same account, so it is a second location rather
than an independent trust root: its signature over the statement makes silent
edits detectable, but the value still has to be compared against something you
obtained elsewhere.

The updater downloads `route10-dnscrypt-proxy-<tag>.tar.gz` and its `.sig`
from the release assets, and verifies the signature **before** extracting or
writing anything into the install tree. There is no "allow unverified" flag.

### First update on a device without the key

A device installed before this check existed has no `conf/release-pub.pem`,
and the old updater replaces itself before it applies any file, so the key
cannot arrive ahead of the first hardened run. In that one case the updater
unpacks **only** `conf/release-pub.pem` and `lib/vendor/route10-signature.sh`
from the release, verifies the archive signature with that key, and stops if it
does not match. The key is then pinned in the install tree (it is in
`keep_files`, so no later release can replace it) and every subsequent update
is anchored.

This is trust on first use, and it is bounded to that single update - the same
trust the pre-hardening updater granted on every update. Install the key out of
band first to skip it entirely:

```bash
scp conf/release-pub.pem root@<device>:/cfg/dnscrypt-proxy/conf/
```

The catch: on that first run the key that checked the signature arrived inside
the archive being checked, so the signature proves the archive is
self-consistent, not that it is the one you meant to install - whoever can
replace the release asset can replace the key along with it. Compare the
fingerprint above against a copy of it you did not get from this repository
(an offline copy, a device that is already anchored, a posting you already
trust) before the first update. Afterwards the key is in `keep_files`, so no
release can swap it, and the signature is a real boundary.

### Signing a release

The private key is offline and never committed, never in CI, never on a router:

```bash
openssl ecparam -name prime256v1 -genkey -noout -out .release-keys/release-signing-key.pem
openssl ec -in .release-keys/release-signing-key.pem -pubout
# put the printed key in conf/release-pub.pem
```

`.release-keys/` is excluded via `.git/info/exclude`. For each tag:

```bash
gh release download vX.Y.Z --repo unflawed-code/route10-dnscrypt-proxy \
  -p 'route10-dnscrypt-proxy-*.tar.gz'
./scripts/sign-release.sh route10-dnscrypt-proxy-vX.Y.Z.tar.gz
gh release upload vX.Y.Z route10-dnscrypt-proxy-vX.Y.Z.tar.gz.sig
```

`sign-release.sh` verifies the signature against `conf/release-pub.pem` before
exiting, so a wrong key fails on the workstation instead of on every router.

### Rotating the key

Ship the new public key out of band (SSH to the device, write
`conf/release-pub.pem`), then sign later releases with the new private key.
Rotation cannot travel through the update channel - that is the point.

## Release Checklist

Order matters: assets are published only after the notes guard passes, so the
notes come before the signature, not after.

1. **Bump the version** in both places, `VERSION=` in `setup.sh` and
   `scripts/start.sh`:

   ```bash
   grep -n '^VERSION=' setup.sh scripts/start.sh
   ```

2. **Push and wait for `CI`** to pass on `main`:

   ```bash
   git push origin main
   gh run list --branch main -L 3
   ```

3. **Tag the verified commit.** Earlier releases used lightweight tags:

   ```bash
   git tag vX.Y.Z && git push origin vX.Y.Z
   ```

4. **Watch the tag run.** It builds the archive, attaches `.intoto.jsonl`, and
   then either writes notes itself or fails *without* publishing anything:

   ```bash
   gh run list --branch vX.Y.Z --json workflowName,status,conclusion
   ```

5. **Write the release notes by hand.** Generated notes for a release with no
   new pull requests are only a compare link, which the guard rejects with
   `no substantive release notes (N chars ...)`. Edit the body, then re-run just
   the failed job - the artifacts already exist, so nothing is rebuilt:

   ```bash
   gh release edit vX.Y.Z --notes "What changed, in sentences a user can act on."
   gh run rerun <run-id> --failed
   ```

6. **Sign the archive** with the offline key and publish the signature:

   ```bash
   gh release download vX.Y.Z -p 'route10-dnscrypt-proxy-*.tar.gz'
   ./scripts/sign-release.sh route10-dnscrypt-proxy-vX.Y.Z.tar.gz
   gh release upload vX.Y.Z route10-dnscrypt-proxy-vX.Y.Z.tar.gz.sig
   ```

7. **Verify as an outsider would.** In an empty directory, follow
   [Verify A Release](#verify-a-release) steps 1-4: `sha256sum -c`, provenance
   `PASSED`, `Verified OK`, fingerprint matches the value above. A tag that
   fails any of these is not a release yet.

8. **Confirm what devices will install.** The archive must carry the tag's
   version, and a device picks it up through `proxy.sh updater check`:

   ```bash
   tar -xOzf route10-dnscrypt-proxy-vX.Y.Z.tar.gz \
     route10-dnscrypt-proxy-vX.Y.Z/setup.sh | grep '^VERSION='
   ```

   After the update, `.installed-version` and
   `/var/log/dnscrypt-proxy-updater.log` show the new tag. The anchor in
   `conf/release-pub.pem` is in `keep_files`, so the release cannot replace it.

## Verify A Release

### 1. Download

```bash
tag=vX.Y.Z
repo=unflawed-code/route10-dnscrypt-proxy
base="https://github.com/$repo/releases/download/$tag"

for f in "route10-dnscrypt-proxy-$tag.tar.gz" \
         "route10-dnscrypt-proxy-$tag.tar.gz.sig" \
         "route10-dnscrypt-proxy-$tag.tar.gz.intoto.jsonl" \
         "SHA256SUMS"; do
  curl -fsSLO "$base/$f"
done
```

### 2. Integrity

```bash
sha256sum -c SHA256SUMS
```

Expect `route10-dnscrypt-proxy-vX.Y.Z.tar.gz: OK`. This catches a truncated or
corrupted download. It does not catch a tampered release: the checksums come
from the same place as the archive.

### 3. Provenance

```bash
slsa-verifier verify-artifact "route10-dnscrypt-proxy-$tag.tar.gz" \
  --provenance-path "route10-dnscrypt-proxy-$tag.tar.gz.intoto.jsonl" \
  --source-uri "github.com/unflawed-code/route10-dnscrypt-proxy" \
  --source-tag "$tag"
```

The verifier should confirm that the artifact was produced by `github.com/unflawed-code/route10-dnscrypt-proxy` from the expected tag. CI runs this same command (pinned to `slsa-verifier` v2.7.1) when it publishes a release, so a tag whose provenance does not verify fails the release job.

### 4. Signature

The archive carries the public key that signed it, at `conf/release-pub.pem`.

```bash
tar -xzf "route10-dnscrypt-proxy-$tag.tar.gz" \
  "route10-dnscrypt-proxy-$tag/conf/release-pub.pem"

openssl dgst -sha256 -verify "route10-dnscrypt-proxy-$tag/conf/release-pub.pem" \
  -signature "route10-dnscrypt-proxy-$tag.tar.gz.sig" \
  "route10-dnscrypt-proxy-$tag.tar.gz"
```

Expect `Verified OK`; a wrong key or an edited byte gives `Verification failure`.
Then confirm it is the expected key:

```bash
openssl pkey -pubin -in "route10-dnscrypt-proxy-$tag/conf/release-pub.pem" \
  -outform DER | sha256sum
```

If that does not match the fingerprint above, stop and do not install. This is
the one step that needs a value from outside the download.

### 5. Install

```bash
tar -xzf "route10-dnscrypt-proxy-$tag.tar.gz"
scp -r "route10-dnscrypt-proxy-$tag"/* root@<device>:/cfg/dnscrypt-proxy/
ssh root@<device> \
  'chmod 700 /cfg/dnscrypt-proxy/*.sh /cfg/dnscrypt-proxy/scripts/*.sh
   /cfg/dnscrypt-proxy/setup.sh
   /cfg/dnscrypt-proxy/proxy.sh start'
```

`setup.sh` installs the pinned dnscrypt-proxy engine; `proxy.sh start` performs
the dnsmasq cutover and rolls back if DNSCrypt does not resolve.

### What Each Check Prevents

| Failure | Caught by |
| --- | --- |
| Truncated or corrupted download | step 2 |
| Archive swapped on a mirror or by a hostile network | step 4 |
| Release built from a different commit or tag | step 3 |
| Future update signed with a substituted key | the key pinned on the device |

Only the last one protects an already-installed system: the updater verifies
every release against `conf/release-pub.pem` on the device and refuses to apply
anything that does not verify, with no override flag.

### If Something Fails

Delete the download and do not install it. Re-fetch; if the failure repeats,
compare the fingerprint before doing anything else. A signature failure is never
a transient error to retry around - treat the release as untrusted and report it.
